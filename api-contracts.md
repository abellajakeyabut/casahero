# CasaHero API Contracts

The HTTP endpoints the UI calls or mocks today, as of 2026-10-25.

## Overview

| Method | Path | Called by UI | Express server | MSW mock |
|---|---|---|---|---|
| `POST` | `/casahero-api/signup` | Yes | Yes | Yes (1s delay) |
| `POST` | `/casahero-api/login` | Yes | Yes | Yes (1s delay) |
| `POST` | `/casahero-api/logout` | Yes | Yes | Yes (3s delay) |
| `GET` | `/casahero-api/me` | Yes | No | Yes |
| `POST` | `/casahero-api/auth/:provider` | No | No | Yes (1s delay) |
| `POST` | `/casahero-api/listings` | No | No | Yes (3s delay) |
| `POST` | `/casahero-api/regions` | Yes | No | Yes (2s delay) |
| `GET` | `/casahero-api/cities` | Yes | No | Yes (2s delay) |
| `GET` | `/casahero-api/types` | Yes | No | Yes (2s delay) |
| `GET` | `/casahero-api/landlords` | No | No | Yes |
| `GET` | `/casahero-api/leases` | No | No | Yes |
| `GET` | `/casahero-api/test` | No | No | Yes |

Sources:
- Client calls: `casahero-ui/src/api/auth.js`, `casahero-ui/src/api/listings.js`, `casahero-ui/src/features/authentication/useMe.js`
- React Query hooks: `casahero-ui/src/hooks/useListings.js`, with query keys in `casahero-ui/src/hooks/listingKeys.js`
- Server: `casahero-server/server.js`
- Mocks: `casahero-ui/src/mocks/handlers.js`, with mock data in `casahero-ui/src/mocks/db.js`. Most listings are generated by `casahero-ui/src/mocks/seedListings.js`: 10 properties per city and 15 units per property, with real Singapore streets and postal sectors.

## Conventions

**Base URL.** The client uses `VITE_API_URL`, or `/casahero-api` when that isn't set (see `casahero-ui/src/api/api.js`).
- **Development:** `.env` sets `http://localhost:5173/casahero-api` and `VITE_ENABLE_MOCKS=true`. That is the Vite dev server, and MSW intercepts the requests in the browser.
- **Production:** the Express server serves the UI and the API from the same origin on port `3000`.

**Request format.** JSON, sent with `Content-Type: application/json`. The axios client times out after 10 seconds.

**Response format.** The auth endpoints return HTTP `200` with this envelope:

```json
{ "outcome": "<human-readable message>", "success": true }
```

| Field | Type | Description |
|---|---|---|
| `success` | boolean | Whether the operation succeeded. The UI branches on this field. |
| `outcome` | string | A message for display or logging. |

The lookup and data endpoints (`listings`, `regions`, `cities`, `types`, `landlords`, `leases`) return a bare JSON array with no envelope.

**Errors.** There is no shared error contract yet.
- Auth endpoints report failure as HTTP `200` with `success: false`. Only the mocks do this; the Express server always returns `success: true`.
- `GET /me` returns `401` with `{ "error": "Invalid Login" }` when nobody is logged in.
- `POST /auth/:provider` returns `400` for an unknown provider.
- On the client, a non-2xx response or a network failure makes axios throw. The login page catches that and shows "Could not reach the server".

**Authentication.** No tokens or sessions exist yet. After login, the UI keeps the user in `userContext` and also writes it to `localStorage` under `userContext`. The `/me` mock reads it back from there.

## Auth

### `POST /casahero-api/signup`

Creates an account. Called from `Signup.jsx` through `signup()`.

Request body:

```json
{
  "name": "Tan Wei Ming",
  "email": "tan.weiming@example.com",
  "password": "secret",
  "confirmPassword": "secret",
  "role": "landlord"
}
```

| Field | Type | Required | Notes |
|---|---|---|---|
| `name` | string | Yes | Full name. |
| `email` | string | Yes | |
| `password` | string | Yes | |
| `confirmPassword` | string | No | Sent today, but only needed on the client (see Known issues). |
| `role` | string | Yes | `tenant` or `landlord`, from the toggle on the signup form. It starts as the `?role=` query parameter (the landing page links to `/signup?role=landlord`), then the role in the user context, then `tenant`. |

Response `200`:

```json
{ "outcome": "Signup successful!", "success": true }
```

Mock only: if the email already belongs to a landlord or tenant in `db.js`, or to a user who already signed up (case-insensitive), it returns:

```json
{ "outcome": "Email already registered", "success": false }
```

Otherwise the mock stores the new user in memory (with `default_role` from `role` (anything other than `landlord` becomes `tenant`), `auth_provider: "email"`, and `full_name` from `name`) together with their password, so they can log in through the login mock. The list resets when the page reloads.

UI behavior: when `success` is `true`, the UI shows the success modal.

### `POST /casahero-api/login`

Logs a user in. Called from `AuthProvider.authenticate()` through `login()`.

Request body:

```json
{ "username": "", "email": "tan.weiming@example.com", "password": "secret" }
```

| Field | Type | Required | Notes |
|---|---|---|---|
| `email` | string | Yes | The login form writes the typed value here. |
| `username` | string | No | Still in the initial form state, so it is sent as `""`. The mock falls back to it when `email` is empty. |
| `password` | string | Yes | |

The role the user picks (`tenant` or `landlord`) is **not** sent.

Response `200`:

```json
{
  "outcome": "login successful!",
  "success": true,
  "user": {
    "id": "ll-001",
    "email": "jake@gmail.com",
    "full_name": "Tan Wei Ming",
    "phone": "+65 9123 4567",
    "avatar_url": null,
    "default_role": "landlord",
    "auth_provider": "google",
    "created_at": "2026-01-05T09:00:00Z"
  }
}
```

`user` has the same shape as a landlord or tenant (see [`GET /landlords`](#get-casahero-apilandlords)). The Express server doesn't return `user` at all.

Mock behavior:
- The password `wrong` returns `{ "outcome": "Invalid email or password", "success": false }`, to test the failure path.
- A known email returns that landlord or tenant.
- An email registered through the signup mock returns that user (without the password), but only if the password matches. Otherwise it returns the "Invalid email or password" failure.
- Any other login returns a generated user with `default_role: "tenant"` and `auth_provider: "email"`.

UI behavior:
- `success: true`: the UI merges `user` into `userContext`, sets `loggedIn: true`, saves it to `localStorage`, then goes to `/listings`, which redirects to the role's home (`/landlord` or `/tenant`).
- `success: false` or a missing body: the UI shows "Invalid username or password."
- The request throws: the UI shows "Could not reach the server."

### `POST /casahero-api/logout`

Logs a user out. Called from `TopBanner.jsx` through `logout()`.

Request body: the current `userContext`, spread as-is:

```json
{ "default_role": "landlord", "loggedIn": true, "email": "jake@gmail.com" }
```

Response `200`:

```json
{ "outcome": "logout successful!", "success": true }
```

UI behavior: when `success` is `true`, the UI clears `userContext` and goes to `/login`.

### `GET /casahero-api/me`

Returns the logged-in user. Called by `SafeRoute.jsx` through the `useMe()` hook, which guards protected routes. The hook doesn't retry and caches the result for 5 minutes.

Response `200`: the stored `userContext`.

```json
{ "default_role": "landlord", "loggedIn": true, "id": "ll-001", "email": "jake@gmail.com", "full_name": "Tan Wei Ming" }
```

Response `401` (nobody logged in):

```json
{ "error": "Invalid Login" }
```

UI behavior: on `200`, `SafeRoute` copies the body into `userContext` and renders the page. On an error or an empty body, it redirects to `/login`.

### `POST /casahero-api/auth/:provider`

Social login. `socialLogin()` in `auth.js` is meant to call it, but no component does yet: `SocialButtons` takes an `onSelect` prop that neither `Login.jsx` nor `Signup.jsx` passes.

Path parameter:

| Name | Values |
|---|---|
| `provider` | `google` or `facebook` |

Request body (optional):

```json
{ "role": "landlord" }
```

| Field | Type | Required | Notes |
|---|---|---|---|
| `role` | string | No | `tenant` (default) or `landlord`. Picks which user list to sign in from. |

Response `200`: the envelope, with the user's fields at the **top level** (not under `user` as in login).

```json
{
  "outcome": "google login successful!",
  "success": true,
  "id": "ll-001",
  "email": "jake@gmail.com",
  "full_name": "Tan Wei Ming",
  "default_role": "landlord",
  "auth_provider": "google"
}
```

Response `400` (unknown provider):

```json
{ "outcome": "Unsupported provider: twitter", "success": false }
```

## Listings

### `POST /casahero-api/listings`

Searches properties. Called from `SearchResults` on the public `/search` page through `useListings(filters)`. The filters come from the page URL, which the landing page and the Listings page set when the user presses Search.

Request body:

```json
{ "type": "HDB", "region": "East", "city": "Tampines", "bed": 2, "bath": 1 }
```

| Field | Type | Required | Notes |
|---|---|---|---|
| `type` | string | No | Property type from [`GET /types`](#get-casahero-apitypes). Matched against the property's `property_type`. |
| `region` | string | No | From [`POST /regions`](#post-casahero-apiregions). |
| `city` | string | No | From [`GET /cities`](#get-casahero-apicities). |
| `bed` | integer | No | Minimum bedrooms. Left out when the user picks "Any". |
| `bath` | integer | No | Minimum bathrooms. Left out when the user picks "Any". |

`type`, `region` and `city` are exact matches and only apply when non-empty. `bed` and `bath` filter each property's `units` to those with at least that many; when either is set, properties left with no units are dropped.

Response `200`: an array of properties, each with its units nested.

```json
[
  {
    "id": "pr-001",
    "landlord_id": "ll-001",
    "name": "Tampines Central Flat",
    "address": "Blk 821 Tampines Street 81",
    "postal_code": "520821",
    "region": "East",
    "city": "Tampines",
    "type": "Residential",
    "property_type": "HDB",
    "created_at": "2026-01-06T09:00:00Z",
    "units": [
      {
        "id": "un-001",
        "property_id": "pr-001",
        "unit_number": "#08-112",
        "bedrooms": 3,
        "bathrooms": 2,
        "area_sqft": 1001,
        "asking_rent_cents": 320000,
        "status": "occupied",
        "photo_paths": ["units/un-001/living.jpg"]
      }
    ]
  }
]
```

Property fields:

| Field | Type | Notes |
|---|---|---|
| `id` | string | Prefix `pr-`. |
| `landlord_id` | string | References a landlord (`ll-`). |
| `name` | string | |
| `address` | string | |
| `postal_code` | string | Six digits. Kept as a string to preserve leading zeros. |
| `region` | string | |
| `city` | string | |
| `type` | string | Category, for example `"Residential"` or `"Landed"`. |
| `property_type` | string | `"HDB"`, `"Condo"` or `"Landed"`. The `type` filter matches this field. |
| `created_at` | string | ISO 8601 timestamp, UTC. |
| `units` | Unit[] | Units whose `property_id` matches and that pass the `bed`/`bath` filters. |

Unit fields:

| Field | Type | Notes |
|---|---|---|
| `id` | string | Prefix `un-`. |
| `property_id` | string | References a property (`pr-`). |
| `unit_number` | string | For example `"#08-112"`. |
| `bedrooms` | integer | |
| `bathrooms` | integer | |
| `area_sqft` | integer | |
| `asking_rent_cents` | integer | In the smallest currency unit. `320000` means SGD 3,200.00. |
| `status` | string | For example `"occupied"`. |
| `photo_paths` | string[] | Storage paths for unit photos. |

### `POST /casahero-api/regions`

Lists regions for the Region dropdown. Called by `SearchBar` through `useRegions()`. Uses `POST` with no body (see Known issues).

Response `200`:

```json
[{ "region": "East" }, { "region": "West" }, { "region": "North-East" }]
```

The mock returns nine regions: East, West, North, South, Central, North-West, North-East, South-East and South-West.

### `GET /casahero-api/cities`

Lists the cities in a region, for the City dropdown. Called by `SearchBar` through `useCities(region)`. The hook only runs once a region is selected.

Query parameters:

| Name | Required | Notes |
|---|---|---|
| `region` | Yes | Exact region name. If it's missing, the mock uses `North-East`. |

Example: `GET /casahero-api/cities?region=North`

Response `200`:

```json
[
  { "region": "North", "city": "Woodlands" },
  { "region": "North", "city": "Yishun" }
]
```

A region with no cities in the mock data returns `[]`.

### `GET /casahero-api/types`

Lists property types for the type pills on the search bar. Called by `SearchBar` through `useTypes()`.

Response `200`:

```json
[{ "type": "HDB" }, { "type": "Condo" }, { "type": "Landed" }]
```

## Known issues

1. **Listing and `/me` requests double the path prefix.** `listings.js` and `useMe.js` call paths like `/casahero-api/regions` on a client whose base URL already ends in `/casahero-api`, so the request goes to `/casahero-api/casahero-api/regions`. MSW still matches because its patterns start with `*`, but a real server wouldn't. `auth.js` does it correctly (`/login`).
2. **`socialLogin()` never fills in the provider.** It uses single quotes, so it posts to the literal path `/auth/${provider}`, and `provider` isn't a parameter of the function anyway.
3. **`regions` uses `POST` for a read.** It sends no body and should be `GET`, like `cities` and `types`.
4. **Social login and login return the user differently.** Login nests it under `user`; social login spreads its fields into the top level.
5. **The server ignores request bodies.** `server.js` has no `app.use(express.json())`, so `req.body` is `undefined`. Signup and login succeed for any input.
6. **The server always succeeds.** None of the auth endpoints validate input, and none can return `success: false`.
7. **The role isn't part of login.** The server can't tell whether a user is a tenant or a landlord. The UI trusts the toggle on the login page.
8. **`confirmPassword` is sent to the server.** It should be checked on the client and removed from the request body.
9. **Logout sends the whole `userContext`.** The server has no session to end, so the body isn't used.
10. **Most endpoints exist only as mocks.** Only `signup`, `login` and `logout` are in the Express server. In production, everything else returns `index.html` from the catch-all route. That includes `/me`, which every protected route depends on.
